# Installation scoreboard credential proposal

Dated 2026-11-13 UTC; proposal only. Strategy review precedes implementation or minting. Targets supplied by the assignment: installation `23475464`, later the actual immutable installation ID behind `install4`. Neither identity, owner, environment, membership nor running deployment was verified. Do not treat `install4` as a token scope until resolved. These are platform installations, not assumed GitHub App installation IDs.

## Existing capability

At platform `86030a5c51a7774132693e8715da2a22e3676b56`:

- `src/platform/auth.ts:68` rechecks membership with viewer < editor < owner. An existing authenticated person can be granted viewer via owner-only `POST /api/installations/:id/members` with `{"login":"<existing approved person>","role":"viewer"}` (`src/installations/routes.ts:88`); DELETE of that membership revokes it. Email invitations remain pending until verified sign-in; no invitations were sent here. A normal cookie is account/user scoped, lasts seven days, and can reach every installation that person belongs to. It is not a durable installation bearer, and a viewer role is not a global HTTP GET-only policy.
- `GET /api/installations/:id` and `/events` and `GET /api/delivery/installations/:id/releases` have membership reads. Detail/events/release output is broad: settings, identifiers, actor IDs, event data and release metadata require review before third-party scoreboard exposure. Some GETs elsewhere perform reconciliation, refresh, export or provider reads. Granting every GET is unsafe.
- `POST /api/widget/authorize` (`src/accounts/oauth.ts:117`) requires at least editor, binds one installation, and inherits the current source session expiry. The widget allowlist in `src/platform/auth.ts:82` permits chat, scene edits, change/job creation and preview operations. Logout deletes derived widget grants. It is not a viewer token; an owner/editor cookie must not be repackaged as scoreboard access.
- Smoke credentials (`src/accounts/smoke-credential.ts:11,38`) last 300 seconds and only allow session/list/plans/version/catalogue plus logout. They cannot read installation detail/events/releases. Operator/test-session credentials are also inappropriate; do not widen them.
- `docs/runbooks/tools/mint-installation-token.mjs` is a one-hour GitHub App repository credential, not platform scoreboard authority. `TOKEN_ACCESS=read` means source contents, not platform installation status. Business seed-agent tokens (`src/business/agent-policy/seed-token.ts:21`) target a linked seed's `/mcp`, not the platform scoreboard. Neither solves this request.

**Conclusion:** human viewer membership exists; an independently revocable, durable, narrowly scoped scoreboard bearer does not exist in the inspected auth path. No existing credential should be copied or minted for this purpose.

## Smallest proposed durable capability

A single opaque 256-bit bearer for one installation and one deployment origin; server stores only its SHA-256 hash, random credential ID, installation ID, issuing owner, fixed scope, created/expiry/revocation times and last-use time. The raw token is returned once to the owner, never recoverable. Use the existing randomToken/hash primitives, not a new signing service. Bind environment implicitly to that platform database/origin, explicitly record the expected audience, and refuse cross-origin use.

Proposed scope: `scoreboard:read` only. Proposed dedicated door: `GET /api/installations/:id/scoreboard`, returning only installation ID/display name, state, observed-at timestamp, current release ID, accepted customer commit, artifact digest, active Worker version and health status when actually observed. Missing provenance remains null/unknown. A release timestamp is not a fresh health observation. Use the installation's existing state projection and PR397's eventual provenance projection; do not implement a duplicate source/artifact/runtime join. If actor reporting is needed, consume the existing event-actors writer's reviewed public projection after it lands; do not expose raw events by default.

Owner-only proposed create/list/revoke doors under `/api/installations/:id/viewer-tokens`; full browser session plus current owner membership and same-origin checks, no widget/company/smoke/scoreboard-token delegation. Creation rechecks authority atomically. Requests recheck current active installation and issuing owner authority, expiry and revocation. Loss of owner authority, owner erasure, disconnect, token revocation or installation deletion ends access. Human viewer membership is not silently created. One token per scoreboard consumer per installation, never a multi-installation token; install4 gets a separate grant after its identity is resolved and strategy approves.

Suggested lifecycle: seven-day default, thirty-day maximum, explicit owner renewal/rotation; no perpetual credential or automatic refresh. This is durable across restarts, not permanent. Keep overlap to one deliberate rotation window, revoke old immediately after consumer replacement. Expired/revoked/foreign tokens return generic 401/403 with no installation discovery. Rate-limit, audit token ID and decision without raw token, use `Cache-Control: no-store`, prohibit URL/query tokens, disable credentialed CORS for public origins, and protect hashed-token comparisons consistently with existing auth. Scoreboard token cannot reach session, billing, members, configuration, secrets, source, artifacts, exports, chat, Business, provider connections or any mutation; default refusal applies to new routes and ambiguous encodings.

Store raw bearer only in the approved consumer's secret store/private 0600 file outside repositories and evidence. A server-side scoreboard fetch adds Authorization; rendered browser HTML and JavaScript never contain it. Logs, traces, crash reports, shell history, analytics, shared screenshots and report refs must exclude it. A public scoreboard can republish only a reviewed non-secret projection and needs a separate owner publication decision. Installation ID obscurity is not authorization. Hash storage reduces database-leak exposure, but a stolen live bearer can read its permitted data until revoked; this is not proof-of-possession authentication.

## Separate implementation bound, not implemented

Platform only: one additive numbered migration after current main's `147` (choose number again at build time); one small capability-auth module and typed context field, owner create/list/revoke handlers and one dedicated projection route. Reuse membership/installation lifecycle gates. Do not special-case installation numbers in source. No delivery changes, provider scopes or private-key setup. Estimate 3–5 builder run-hours plus 1–2 independent auth/data gate run-hours, separate from Assisted rehearsal and org-target work.

Required public-door tests: token reads only its approved projection; second installation/cross-origin/ambiguous path refused; every POST/PUT/PATCH/DELETE and sensitive GET refused; expiry, explicit revoke, owner change, disconnect and erasure immediately stop access; normal owner/viewer/widget behavior preserved; no raw token in retained data/logs/response after initial issue. Integrate PR397 after its normal review/landing, preserve historical unknown values, and coordinate event-actors changes with its existing writer. Strategy sees this document first. **Nothing minted or implemented.**
